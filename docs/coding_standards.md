# Python 代码注释规范

## 1. 目标

本项目要求 Python 代码具备较详细的中文注释和 Docstring。

注释的目标是帮助后续开发人员快速理解：

* 模块负责什么；
* 为什么这样设计；
* 输入和输出是什么；
* 数据如何流转；
* 核心算法如何工作；
* 关键参数有什么意义；
* 存在哪些风险和边界情况；
* 当前模块与上下游模块是什么关系。

注释应尽可能详细，但**不要求逐行注释**。

---

## 2. 总体原则

优先对以下内容添加注释：

* 模块；
* 类；
* 函数和方法；
* 复杂逻辑块；
* 核心算法；
* 业务规则；
* 数据转换；
* 异常处理；
* 重要设计决策。

简单赋值、普通循环、明显条件判断、简单 return 等无需机械注释。

注释应优先解释：

> 为什么这样实现。

而不是简单重复：

> 代码正在做什么。

---

## 3. 注释语言

以下内容原则上统一使用中文：

* 模块 Docstring；
* Class Docstring；
* Function / Method Docstring；
* 业务逻辑注释；
* 算法说明；
* 风险说明。

变量名、函数名、类名、模块名继续使用英文。

BM25、Embedding、Retriever、Reranker、RRF、Recall@K 等专业术语可直接保留英文。

---

## 4. 模块级 Docstring

核心 Python 文件顶部必须包含模块级 Docstring。

应根据实际情况说明：

* 模块职责；
* 主要输入；
* 主要输出；
* 核心流程；
* 与其他模块的关系；
* 在系统中的位置。

不要只写：

```python
"""检索模块。"""
```

应让阅读者在不深入代码的情况下就能理解模块用途。

---

## 5. Class Docstring

核心 Class 必须添加中文 Docstring。

建议说明：

* 类负责什么；
* 为什么需要这个类；
* 核心工作流程；
* 重要属性；
* 与其他组件的关系；
* 需要注意的限制。

Parser、Chunker、Retriever、Reranker、Evaluator、Generator 等核心类应重点说明。

---

## 6. Function / Method Docstring

公开函数和方法必须添加中文 Docstring。

复杂内部函数也应添加。

根据函数复杂程度说明：

* 功能；
* 业务目的；
* Args；
* Returns；
* Raises；
* 重要规则；
* 边界情况；
* 对上下游的影响。

不要为了格式完整而填写大量没有实际意义的说明。

---

## 7. 参数说明

重要参数应说明业务意义，而不只是类型。

例如：

```text
top_k:
    Retriever 返回的最大候选条款数量。
    该参数会影响法规召回率、Reranker 候选规模和后续 Context 长度。
```

以下参数必须重点解释：

* Top-K；
* 阈值；
* Score；
* 权重；
* 相似度；
* OCR confidence；
* Chunk 长度；
* overlap；
* RRF 参数；
* Hybrid 融合参数。

---

## 8. 逻辑块注释

连续多行代码共同完成一个业务目标时，应在逻辑块前写一段注释。

推荐：

```python
# 将 BM25 和 Embedding Retriever 的返回结果统一为 RetrievalResult。
# 两种 Retriever 的 Score 和返回对象不同，统一格式后可以避免
# Reranker、Evaluator 和 Context Builder 依赖底层检索实现。
```

不推荐：

```python
# 创建列表
results = []

# 遍历列表
for item in items:
```

---

## 9. 算法注释

涉及算法时，应根据复杂程度说明：

* 算法名称；
* 解决什么问题；
* 输入和输出；
* Score 含义；
* Score 越大还是越小越好；
* 关键参数；
* 为什么采用该算法；
* 当前参数是否只是 baseline；
* 后续是否需要 Evaluation 调优。

重点包括：

* BM25；
* Cosine Similarity；
* RRF；
* Score Normalization；
* Hybrid Retrieval；
* Recall@K；
* Precision@K；
* MRR；
* nDCG。

---

## 10. RAG 核心模块

以下代码属于项目核心逻辑，应提供比普通工具函数更详细的注释：

* PDF 解析；
* OCR；
* 法规结构化；
* Chunk；
* Embedding；
* BM25；
* Vector Retrieval；
* Hybrid Retrieval；
* Reranker；
* Retrieval Evaluation；
* Context Builder；
* Citation；
* 检验方案生成；
* Generation Evaluation。

---

## 11. PDF / OCR

PDF 和 OCR 代码应说明：

* 如何判断文本 PDF 与扫描 PDF；
* OCR 在什么情况下触发；
* DPI 等关键参数为什么这样设置；
* confidence 如何使用；
* OCR 失败如何处理；
* 页码如何保留；
* 哪些情况需要人工核验。

涉及 OCR 自动修正时，应说明修正规则和风险。

---

## 12. 法规结构化

法规解析代码应说明：

* 标准编号如何识别；
* 章、节、条、款如何识别；
* 父子层级如何建立；
* 标题与正文如何区分；
* 跨页条款如何处理；
* 条款编号异常如何处理；
* 原始值是否保留；
* 规范化结果如何记录。

可能改变法规原始含义的处理必须特别说明。

---

## 13. Chunk

Chunk 代码应说明：

* 为什么采用当前切分粒度；
* 为什么按条款而不是固定字符切分；
* 如何处理纯标题；
* 如何处理长条款；
* 如何处理父子条款；
* 如何处理跨页内容；
* 如何保证来源可追溯。

---

## 14. Embedding

Embedding 代码应说明：

* 使用的模型；
* 模型用途；
* 输入文本如何构造；
* 是否进行向量归一化；
* 向量维度；
* Query 和 Document 是否使用不同前缀；
* 模型如何加载和缓存。

---

## 15. Retrieval

Retriever 代码应说明：

* Retriever 类型；
* Query 如何处理；
* 检索范围；
* Top-K 如何使用；
* Metadata Filter 如何工作；
* Score 如何计算；
* 结果如何排序。

统一 Retriever 接口应说明设计目的：

> 让上层 RAG 不依赖 BM25、Embedding 或 Hybrid 的具体实现。

---

## 16. Hybrid Retrieval

Hybrid Retrieval 必须说明：

* 为什么同时使用 BM25 和 Embedding；
* 两路结果如何融合；
* 如何去重；
* 如何处理不同 Score 尺度；
* 最终 Top-K 如何产生。

如果使用 RRF，应解释为什么采用排名融合，而不是直接相加原始 Score。

---

## 17. Reranker

Reranker 代码应说明：

* 为什么 Retriever 后还需要重新排序；
* 输入候选数量；
* 输出候选数量；
* Reranker Score 的含义；
* 与 Retriever Score 的区别。

---

## 18. Evaluation

Evaluation 代码不能只实现公式。

必须说明每个指标解决的问题，例如：

* Recall@K：应该找到的关键法规找回了多少；
* Precision@K：返回结果中有多少真正相关；
* MRR：第一个正确结果是否足够靠前；
* nDCG：整体排序质量是否合理。

---

## 19. 法规数值与风险

涉及以下数据时应重点注释：

* 压力；
* 温度；
* 壁厚；
* 检测比例；
* 检测等级；
* 周期；
* 尺寸；
* 公差；
* 材料参数。

对于 OCR 可能识别错误的关键数字，应尽量保留：

* 原始值；
* 规范化值；
* 风险标记；
* 来源页码。

不得在低置信度情况下静默修改关键法规数值。

---

## 20. Citation 与来源追溯

Citation 相关代码应说明：

* 生成结论如何对应 Chunk；
* Chunk 如何对应法规条款；
* 条款如何对应标准；
* 如何追溯到原始 PDF 页；
* 如何验证引用是否真实存在。

目标是支持：

```text
生成结论
→ Citation
→ 法规条款
→ 标准
→ 原始 PDF
```

---

## 21. 异常处理

重要异常处理应说明：

* 为什么可能发生；
* 为什么选择继续或终止；
* 是否影响其他文件；
* 是否记录日志；
* 是否需要人工检查；
* fallback 是否降低结果可靠性。

禁止无说明地使用：

```python
except Exception:
    pass
```

---

## 22. 已知限制

如果代码存在明确限制，应在最相关的位置说明。

例如：

* OCR 无法可靠恢复复杂表格二维关系；
* 当前规则无法识别某类特殊条款编号；
* 当前参数只是实验 baseline；
* 某类 PDF 暂未支持。

注释必须与实际能力一致。

---

## 23. TODO

TODO 必须具体。

不推荐：

```python
# TODO 优化
```

推荐：

```python
# TODO:
# 当前条款编号规范化主要依据编号格式判断。
# 后续需要结合前后条款序列进行一致性校验，
# 降低 OCR 将 6.3.3.2 识别为 6.3.32 后造成误修正的风险。
```

---

## 24. 不要求逐行注释

以下代码一般无需单独注释：

* 简单变量赋值；
* 明显条件判断；
* 普通循环；
* 简单 return；
* 标准库常规调用；
* 含义明确的初始化代码。

除非这些代码背后存在重要业务规则。

原则是：

> 一个逻辑块有一段有价值的说明，优于每行都有一句无意义注释。

---

## 25. 注释必须与代码一致

代码发生变化时，应同步检查相关注释。

禁止出现：

* 代码已修改但注释仍描述旧逻辑；
* 参数默认值变化但 Docstring 未更新；
* Retriever 算法变化但注释未更新；
* 数据结构变化但字段说明仍然过时。

错误注释比没有注释更危险。

---

## 26. 修改已有代码

修改已有代码时：

* 保留仍有效的注释；
* 修正过时注释；
* 补充本次涉及的核心逻辑说明；
* 不要求顺便给整个项目所有代码补注释。

除非当前任务明确是“代码注释整改”。

---

## 27. 禁止无关注释重构

为了补充注释，不得擅自：

* 修改业务逻辑；
* 修改函数签名；
* 修改数据模型；
* 修改数据库 Schema；
* 修改算法；
* 修改 Prompt；
* 修改测试预期；
* 删除已有功能；
* 进行无关重构。

发现其他问题可以记录，但不要借补注释扩大任务范围。

---

## 28. 测试代码

测试代码不要求和核心业务代码相同的注释密度。

复杂测试应说明：

* 测试目的；
* 业务场景；
* 为什么选择当前测试数据；
* 防止什么回归问题。

测试名称已经足够清楚时，无需重复注释。

---

## 29. scripts

重要脚本应说明：

* 脚本用途；
* 输入；
* 输出；
* 是否修改数据；
* 输出目录；
* 是否可以重复执行；
* 是否会覆盖已有结果。

全库处理脚本应明确说明运行影响。

---

## 30. 完成前检查

Codex 每次新增或修改 Python 代码后，应检查：

* 核心模块是否有模块 Docstring；
* 核心 Class / Function 是否有 Docstring；
* 复杂逻辑是否有中文说明；
* 算法是否解释设计原因；
* 关键参数是否解释；
* 法规处理是否说明风险；
* 注释是否与代码一致；
* 是否存在大量无意义逐行注释。

---

## 31. 最终原则

本项目注释规范总结为：

> 尽可能详细解释重要代码，但不逐行解释简单代码。

> 重点解释为什么，而不仅仅解释做什么。

> 重点记录业务规则、数据流、算法、参数、风险和设计决策。

> 让未来维护人员无需重新推导整个实现思路，就能理解代码。
