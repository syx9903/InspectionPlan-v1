# TASK-002.10.2 PP-StructureV3 表格输出质量与中文兼容性报告

## 1. 实验目的

检测到 `table` 只证明区域分类成功；即使 HTML 行列正确，中文、标准号或关键数字
仍可能识别错误。本实验用3个真实法规页面、5张表验证编码链、二维结构和关键cell，
判断其是否值得进入后续独立 Table Schema 设计。

| PQ-015 | 119 | 3 | 规则型4列表，中文、条款号、双圈号数字 |
| PQ-016 | 120 | 1 | 续表，水印干扰、条款号、双圈号数字 |

## 3. 中文“乱码”定位

TASK-002.10.1 中看到的 `±í`、`ÖÐ...` **不是 raw JSON 编码损坏，也不是OCR
内部输出乱码**。逐层证据如下：

| 层次 | 结果 | 证据 |
|---|---|---|
| PP-Structure Python对象 | 正常Unicode | PQ-016直接对象中为“序号”“损伤模式” |
| `table_ocr_pred.rec_texts` | 正常中文 | `repr`为 `\u5e8f\u53f7` 等正确码点 |
| `pred_html` | 正常中文 | Python `ascii()`显示正确Unicode转义 |
| JSON写出 | 正常UTF-8 | `encoding="utf-8"`、`ensure_ascii=False` |
| JSON重新读取 | 与写前完全相等 | 3/3 `unicode_round_trip_ok=true` |
| 文件字节 | 无BOM UTF-8 | 3/3 `utf8_bom_present=false` |
| 默认Windows控制台捕获 | 曾显示乱码 | 默认GBK输出经外部工具链再次解释后失真 |
| 强制UTF-8控制台 | 正常显示 | 设置 `PYTHONIOENCODING=utf-8` 后中文正常 |

因此不需要也不允许对文件执行GBK反解。若把正常Unicode“修复”一次，反而会破坏
真实数据。控制台显示问题必须与OCR recognition error分开。

## 4. UTF-8 round-trip

流程：

```text
Python dict
→ json.dumps(ensure_ascii=False)
→ UTF-8写出
→ UTF-8重新读取
→ 对象完全相等比较
```

| sample_id | round-trip | BOM |
|---|---|---|
| PQ-015 | pass | 无 |
| PQ-016 | pass | 无 |
| PQ-012 | pass | 无 |

测试3个，成功3个，失败0个。

## 6. 中文 cell 结果

| sample | checked | exact | wrong/minor | exact rate |
|---|---:|---:|---:|---:|
| PQ-015 | 8 | 8 | 0 | 100.00% |
| PQ-016 | 7 | 6 | 1 | 85.71% |
| PQ-012 | 6 | 4 | 2 | 66.67% |
| 合计 | 21 | 18 | 3 | 85.71% |

主要中文错误：

- 水印字符混入：原文“微动腐蚀”输出为“SAC 微动腐蚀”。
- 多字符：原文“SAW、ESW”输出为“SAW、dESW”。
- 标点缺失：“（限碱性药皮焊条）”缺失右括号。

这些是识别/分区错误，不是编码错误。

## 7. 数字 cell 结果

数字按逐字符完全一致判定；圈号数字不能只按数值大致相同判为正确。

| sample | checked | exact | wrong | exact rate |
|---|---:|---:|---:|---:|
| PQ-015 | 12 | 7 | 5 | 58.33% |
| PQ-016 | 14 | 8 | 6 | 57.14% |
| 合计 | 26 | 15 | 11 | 57.69% |

普通条款号 `7.6`、`7.10`、`9.3`、`9.10` 均表现较好。主要失败集中在双圈号：

- `①⑦` → `①`
- `⑤⑨` → `9`
- `⑥⑥` → `66`
- `②⓪` → `2`
- `③①` → `③`
- `①④` → `?`

数字列仍落在正确单元格，但字符内容不可靠。对于法规标引序号，这类错误足以造成
错误引用，因此当前输出不能直接作为法规检验条件来源。

## 8. 单位、标准号与条款号

- 单位样本：`475℃`，1/1 exact。当前没有覆盖 `%`、`MPa`、`mm`，不能外推。
- 标准号：`NB/T 47018.2/.3/.4/.5/.6/.7`，6/6 exact。
- 普通条款号：本次抽检均正确。
- 特殊圈号标引：显著不可靠，应与普通阿拉伯数字分开评估。

## 9. 主要失败模式

1. 双圈号只保留一个字符。
2. 圈号退化为普通阿拉伯数字或问号。
3. 页面水印被吸收到单元格文本。
4. 拉丁缩写多出字符。
5. 括号等标点缺失。
6. 控制台默认编码造成“看起来乱码”，但文件本身正确。

本次未发现行列错位或合并单元格结构错误。

## 11. 是否适合进入 Table Schema 设计

选择 **B：结构可靠，但文本/数字仍需额外质量层。**

进入独立 Table Schema 设计有价值，因为5/5表格结构正确，且能够保存HTML、cell box、
rowspan和colspan。但设计必须同时保存原图定位、原始OCR值、cell坐标、来源页码和
人工核验风险；特殊数字不得静默纠错或直接作为法规依据。

## 12. 两个核心问题

### 中文乱码是不是编码问题

不是文件编码问题。Python对象、HTML和UTF-8 JSON中的Unicode都正确，3/3
round-trip完全相等。先前乱码来自Windows默认控制台输出与外部捕获链的转码。

### 关键数字是否足够可靠

不够可靠。26个数字cell仅15个逐字符exact，当前样本准确率57.69%；圈号标引尤其
危险。结构结果可以进入Schema设计，但数字内容不能直接成为法规检验条件证据。

## 13. 人工复核方法

1. 打开 `data_processed/table_experiments/<sample_id>/table_###.html`。
2. 根据 `summary.json` 的PDF路径和页码打开原页。
3. 对照 `normalized.json` 的行、列、rowspan、colspan。
4. 逐字符核对 `summary.json` 的 `cell_checks`，尤其双圈号。
5. 查看 `python_repr.json` 中的Unicode转义。
6. 查看 `round_trip.json`，应为 `unicode_round_trip_ok=true`。

## 14. 限制

- 仅3页5表，人工标签不是全库Gold。
- 单位只覆盖℃，没有覆盖%、MPa、mm。
- 没有测试无边框表、跨页表或旋转表。
- 没有修复OCR结果，也没有定义正式Table Schema。
